# Shared data and API contracts

These interfaces are the implementation contract for BlackOutBridge. They describe planned behavior, not existing endpoints. Keep the implemented TypeScript and validation schemas consistent with this document. Coordinate contract changes before editing both sides of an integration.

## Money and catalog

```ts
type MoneyConfig = { currency: 'MMK'; scale: 0 };
type CatalogModifier = { modifierId: string; name: string; deltaUnits: number };
type CatalogItem = {
  itemId: string;
  name: string;
  aliases: string[];
  unitPriceUnits: number;
  available: boolean;
  modifiers: CatalogModifier[];
};
type CatalogSnapshot = MoneyConfig & {
  snapshotId: string;
  sourcePosId: string;
  issuedAt: string;
  items: CatalogItem[];
};
type DraftLine = { itemId: string; quantity: number; modifierIds: string[] };
```

Each sellable variant has its own item ID. Amounts and modifier deltas are safe integers in whole kyat units. The first version permits nonnegative modifier deltas only. Quantities range from 1 through 99. Enforce modifier compatibility in catalog validation; unsupported combinations require clarification. Unknown or unavailable items cannot be confirmed.

Line total is `quantity * (unitPriceUnits + sum(selected modifier deltas))`. Reject duplicate modifier IDs, overflow, invalid quantities, and unrecognized identifiers. Compute bill total and cash change from validated lines. Do not accept an amount generated by the model as authoritative.

## Model interpretation boundary

```ts
type InterpretationRequest = {
  instruction: string;
  currentDraft: DraftLine[];
  candidates: CatalogItem[];
};
type CartProposal =
  | { status: 'ready'; lines: DraftLine[] }
  | {
      status: 'needs_clarification';
      question: string;
      candidateItemIds: string[];
    };
type InterpretationResult = {
  proposal: CartProposal;
  inferenceSource: 'ON_DEVICE' | 'IN_CLOUD';
};
```

`ready` means the model proposed a full replacement draft, including the existing lines the user intended to retain. The application validates it and the cashier confirms it. The model cannot set prices, save sales, or mark payments. Reject unknown JSON properties rather than quietly accepting new authority fields.

The application contract uses normalized uppercase labels. Compare the SDK response against its exported InferenceSource enum and map explicitly; the installed SDK's raw values are lowercase `on_device` and `in_cloud`. Do not compare a raw response to a hardcoded uppercase string. Do not label a simulated or cached response as a new on-device response. Malformed output yields one bounded retry or manual correction; it never triggers an unbounded call loop.

## Confirmed records

```ts
type ConfirmedLine = DraftLine & {
  capturedUnitPriceUnits: number;
  capturedModifierDeltaUnits: number;
  lineTotalUnits: number;
};
type PaymentRecord =
  | { status: 'UNPAID'; receivedUnits: 0 }
  | { status: 'CASH_RECORDED'; receivedUnits: number; changeUnits: number }
  | { status: 'EXTERNAL_UNVERIFIED'; receivedUnits: 0; reference: string };
type ConfirmedSale = MoneyConfig & {
  saleId: string;
  sourceDeviceId: string;
  snapshotId: string;
  recordedAt: string;
  lines: ConfirmedLine[];
  totalUnits: number;
  payment: PaymentRecord;
};
type QueueEntry = {
  saleId: string;
  payloadVersion: 1;
  state: 'PENDING' | 'REVIEW_REQUIRED' | 'IMPORTED';
  attempts: number;
  lastErrorCode?: string;
  destinationReceiptId?: string;
};
```

Persist the immutable sale and queue entry in one transaction. `capturedModifierDeltaUnits` is the sum of selected per-item modifier deltas. Validate the captured prices and totals again against the backend-approved historical snapshot during recovery.

An imported order and a payment are independent. Unpaid and externally unverified records require a supported native representation or explicit review; the connector must not convert them into cash sales.

## Connector interface

```ts
type PreviewItem = {
  saleId: string;
  status: 'READY' | 'ALREADY_IMPORTED' | 'REVIEW_REQUIRED';
  issueCodes: string[];
  destinationReceiptId?: string;
};
type ImportResult = {
  saleId: string;
  status: 'IMPORTED' | 'ALREADY_IMPORTED' | 'REVIEW_REQUIRED';
  destinationReceiptId?: string;
  issueCodes: string[];
};
interface PosConnector {
  getCatalog(): Promise<CatalogSnapshot>;
  preview(sales: ConfirmedSale[]): Promise<PreviewItem[]>;
  commit(sales: ConfirmedSale[]): Promise<ImportResult[]>;
  status(saleId: string, sourceDeviceId: string): Promise<ImportResult>;
}
```

Proposed HTTP routes:

| Method and route | Behavior |
| --- | --- |
| GET `/api/continuity/catalog` | Return an authorized snapshot retained by the backend |
| POST `/api/continuity/import/preview` | Accept `{ sales }`; validate without financial writes |
| POST `/api/continuity/import/commit` | Accept `{ sales }`; revalidate and import approved records |
| GET `/api/continuity/import/status/:saleId?sourceDeviceId=...` | Return an authorized prior import result; 404 means no committed record |

Both POST responses return `{ results: [...] }` in input order. Require authentication; derive tenant and location scope on the server. Return a per-sale result for domain conflicts, HTTP 401/403 for access failures, and a retriable error for a failed transaction. Never return a partial sale as imported.

Issue codes include `UNKNOWN_ITEM`, `UNSUPPORTED_MODIFIER`, `SNAPSHOT_MISSING`, `PRICE_MISMATCH`, `TOTAL_MISMATCH`, `PAYLOAD_CONFLICT`, and `UNSUPPORTED_PAYMENT_STATE`. Display actionable messages without exposing private backend logs.

The backend uniqueness key is `(tenantId, sourceDeviceId, saleId)`. Identical retries return the existing destination receipt. Reused IDs with different immutable payloads return `PAYLOAD_CONFLICT`. Store the import ledger and native sale within the same database transaction. Suppress kitchen routing and payment initiation for historical recovered sales.
